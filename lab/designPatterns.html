Testing New Design Patterns

Architecture MVP MVVM Dependency Injection

View the code on GitHub

The Experiment

This lab is about one question: how far can a Unity project scale if you refuse to use Singletons? I tried three things together in Unity 2022.3: the MVP pattern, the MVVM pattern, and a small Object Resolver I wrote to handle dependency injection. It's an architecture test, not a finished game.

The Problem with Singletons

Most Unity projects reach for Manager.Instance everywhere. It's quick, but every script ends up hard-wired to every other one, which makes testing, swapping systems and growing the project harder over time. I wanted to see what a more scalable setup looks like if you have the time to build it properly.

The Object Resolver

The resolver replaces the Singleton. A Bootstrap script creates it when the scene starts, registers the services, and then goes through every MonoBehaviour in the scene and fills in any field marked [Inject] using reflection and the field's type. A script just asks for an interface like IUIService and never needs to know who provides it, so swapping a service means registering a different class and nothing that uses it has to change. Objects spawned later can be injected with InjectIntoInstance. 

public class PlayerUIView : MonoBehaviour
{
    [Inject] private IUIService service;   // filled by the resolver

    public void UpdateMagnitude(float magnitude)
    {
        service.SetText("PLAYER_UI", "magnitudeMVVM", magnitude.ToString());
    }
}

MVP

In the MVP setup the model is a plain C# class that holds data and rules with no Unity code in it. The views are MonoBehaviours hidden behind interfaces like IPlayerMovementView, and a presenter sits between them. When the player moves, the view raises an event, the presenter asks the model for the result, and then tells each view what to show. A small installer creates the model and presenter and connects them, so there's one place to look when something isn't wired up. 

private void HandleMoveInput(Vector2 input)
{
    Vector3 velocity = playerModel.CalculateMovement(input);
    playerMovementView.ApplyMovement(velocity);
    playerMovementUIView.UpdateUI(velocity);
    playerMovementDebugView.SentDebug(velocity);
}

MVVM

MVVM flips who is in control. Instead of a presenter pushing data into views, the views subscribe to values on a ViewModel and update themselves. The glue is a small generic class called ObservableProperty that fires an event only when its value actually changes. The ViewModel listens to the model and turns its data into something a screen can use, such as the speed of the player from its velocity. 

public PlayerViewModel(PlayerModel playerModel)
{
    this.playerModel = playerModel;
    playerModel.velocity.OnValueChanged += v => magnitude.Value = v.magnitude;
}

MVP vs MVVM

I ended up using both on the same player model, and they suited different jobs. MVP worked best for gameplay flow, because the presenter controls the order things happen in. MVVM worked best for UI, because adding a new readout only needs one new binding and no changes to a presenter. Since they share one model, the same player data drives both the movement and the screen.

Combat Actions (Stress Test)

To push the setup further I built an ability system on top of it. Each ability, like Vine, Steam Cloud and Water Surge, is a ScriptableObject, with a matching data MonoBehaviour that carries the runtime state such as the Rigidbody and mouse position. The player picks two spell elements and the model returns the combined ability, and that flow runs through both the MVP and MVVM versions.

What I Learned

Decoupling paid off. I could add or swap views without touching gameplay code, which is exactly what I was hoping for. The cost is setup: the installers and interfaces are real overhead and probably too much for a small project. The resolver also uses reflection and scans every MonoBehaviour at startup, which is fine in this scene but would need caching in a big one.

What I'd Improve Next

The resolver defines Singleton, SceneScoped and Transient lifetimes, but they aren't enforced yet, and pooled objects are still a TODO. I'd also make failed injections more explicit and have the bindings unsubscribe from events when views are destroyed.
