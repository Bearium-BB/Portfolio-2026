At a glance: Solo programmer on a team of three. I built the physics-based hand controls and grab system for a QWOP-like game in Unity, in a three-day game jam.

Overview

  • Role: Solo programmer, on a team of 3 with two artists.
  • Engine: Unity.
  • Event: Winnipeg Game Jam 2026.
  • Duration: three-day game jam.

Controlling the Goblin

The biggest challenge we had to overcome was figuring out how the player would control the goblin. Originally, I applied forces directly based on the player's joystick input. This didn't feel very responsive or reliable, because the character wouldn't always move the way the player intended.

We reworked the system to use the controller's rotation to determine the intended movement direction. From that rotation I calculated a target position in front of the player, which the hands move toward. I then took the direction between the goblin's current position and that target and applied a multiplied force toward it. This lets the goblin gradually move in the direction the player is aiming instead of reacting to raw joystick input alone.

We also added visual cubes to show where the controllers are aiming. They don't move anything themselves, but they give players feedback so they can understand how their controller positioning turns into the goblin's movement.

The movement system: controller rotation, directional target calculation, force application, and the visual target cubes.

Snake Movement

The new movement system also created an unintended technique we ended up calling "snake movement." By coordinating the movement of their hands, players can slither across the floor. We decided to leave it in because we thought it was funny. If someone discovers it, they discover it.

I've always loved how the developers of Dishonored sometimes leave mechanics like this in for the community to find, as long as they aren't too game-breaking. Looking back, going through two iterations of the hand controls improved the game, and it gave us a movement technique that became part of its personality.

The Grab System

Pressing a hand's grab button checks for anything within a small radius of the wrist. If there is something to hold, the wrist is attached to it with a joint (a physics connection that locks two objects together), and pressing the button again lets go. There are two kinds of things to grab. Static objects like walls and ledges are tied to a fixed anchor in the world, so pulling on them drags Jimbo's body across the level. Movable objects are tied to the object itself, so you can drag a box along or throw it around.

Each kind gets its own pull strength, and the hand goes back to a weaker pull when it lets go. Holding a wall is strong and reliable, holding a loose object is heavy and sluggish, and a free hand is the weakest. When both hands are holding on at the same time, the body also gets a single push forward in the direction the head is facing, so locking on with both hands lets you haul yourself along instead of only swinging.

Problem solved: the grab had to feel the same on a static wall and on a loose object, but the two need to behave very differently. Giving each its own joint target and pull strength let one grab button and one set of controls cover both, so the player never has to learn a second rule.

Support Scripts

Once the movement was done, the game still needed animations, an objective and everything else around it, so I wrote a handful of small reusable scripts to help it run. A timer, a trigger zone, a collision hook and a restart key each fire a Unity event, which can be connected to things like a reset or a scene change. A scene loader handles level changes and quitting, and the camera follows the goblin from above with a smoothed lerp. I kept them simple and compact so they can be dragged in and out of a scene without any complicated code, and the on-collision events turned out to be especially useful.

Objects also play impact sounds whose volume scales with how hard they hit, with a little random pitch and a short cooldown so a pile of colliding objects doesn't turn into noise.

What I'd Improve

The grab and pull strengths are hardcoded into the scripts, so adjusting them means editing the code each time. I'd move these values into the Unity Inspector, which would make them adjustable while the game is running and much easier to balance.

I'd also refactor the hand movement scripts. They grew quickly during the jam and still contain leftover experiments and unnecessary code. Some systems are too tightly coupled, and that would make future changes harder than they should be. If the project continued, I'd make the code more modular, readable and maintainable, so new mechanics could be added without working around the technical debt from the jam.
